# Молвест · Поддержка 1С

Актуальное развёртывание на VPS Cloud4box, доступ по IP и подготовка HTTPS описаны в [DEPLOYMENT.md](DEPLOYMENT.md). На этом VPS используется Python venv + systemd + Nginx; Docker-конфигурация ниже остаётся альтернативным способом развёртывания.

Веб-интерфейс для бэкенда из соседней папки `1C_Support_Agent`. Фронтенд, серверный адаптер и конфигурация развёртывания находятся в `web`. В исходном бэкенде также исправлен слишком короткий тайм-аут GigaChat: `app/config/settings.py` и `app/agent/agent.py`. При переносе на сервер используйте актуальную версию обеих папок.

## Возможности

Потоковая выдача и плавное появление ответа для чата и файлов: [реализация и проверки](STREAMING.md).

- Чат с существующим AI-агентом, быстрые темы, Markdown-ответы, отображение ожидания и ошибок.
- Все 33 формата документов исходного `DocumentProcessor` до 40 МБ, изображения PNG/JPEG/WebP до 15 МБ. [Форматы и особенности преобразования](FILE_UPLOADS.md).
- Локальная история диалогов, поиск, удаление из браузера, экспорт в Markdown, копирование ответов.
- Оценка последнего ответа от 0 до 10 с комментарием. Ответ `feedback_id: null` отображается как ошибка сохранения.
- База знаний: поиск, фильтрация, чтение, добавление и редактирование материалов, импорт Markdown/TXT в UTF-8.
- Панель оператора: статистика, динамика обращений, категории и просмотр открытых эскалаций.
- Доступ к административным API по логину и паролю. Пароль существует только на сервере и в памяти открытой вкладки после входа; после обновления страницы требуется повторный вход.
- Адаптивная вёрстка, управление с клавиатуры, диалоги с фокусом, состояния загрузки и пустых данных, локально размещённые шрифты.

Реализация: [страницы](src/presentation/pages), [состояние диалогов](src/application/Workspace.tsx), [клиент API](src/infrastructure/api.ts), [серверный адаптер](server/main.py).

## Стек и структура

React, TypeScript, Vite, React Router, Zod, React Markdown, Lucide. Оформление — обычный CSS. FastAPI-адаптер переиспользует классы исходного бэкенда. На сервере Nginx раздаёт собранный интерфейс и проксирует `/api` в Python-процесс. Node.js нужен для сборки, но не для обслуживания готового сайта.

```text
web/
  src/
    domain/                 типы и проверка контрактов
    application/            состояние и сценарии диалогов
    infrastructure/         HTTP и хранение истории
    presentation/           страницы, компоненты и стили
  server/                   маршруты адаптера, авторизация, база знаний, вложения
  scripts/run_server.py     запуск адаптера вместе с исходным бэкендом
  deploy/                   Dockerfile, Nginx, пример Caddy
  tests/                    тесты API, адаптера и браузерных сценариев
  compose.yaml              запуск полного приложения
```

Версии JavaScript-зависимостей зафиксированы в [package-lock.json](package-lock.json), Python-зависимостей — в [server/requirements.lock](server/requirements.lock). [server/requirements.txt](server/requirements.txt) описывает исходные зависимости для последующего обновления lock-файла.

Выбор Vite для существующего бэкенда соответствует варианту из [документации React](https://react.dev/learn/build-a-react-app-from-scratch). Сборка статического сайта описана в [документации Vite](https://vite.dev/guide/static-deploy).

## Локальный запуск

Нужны Node.js 22.12+ или 24 и Python 3.12. Выполняйте команды в папке `web`.

### Windows PowerShell

```powershell
npm.cmd ci
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r server/requirements.lock
Copy-Item .env.example .env
```

Заполните `.env`:

| Переменная | Назначение |
| --- | --- |
| `GIGACHAT_CREDENTIALS` | Ключ существующего бэкенда; обязателен для его запуска |
| `GIGACHAT_SCOPE` | Область доступа вашей учётной записи GigaChat |
| `GIGACHAT_MODEL` | Модель, доступная вашей учётной записи |
| `GIGACHAT_REQUEST_TIMEOUT` | Тайм-аут одного HTTP-запроса к GigaChat, по умолчанию 30 секунд, допустимо от 1 до 60; целевое время ответа 5 секунд отслеживается отдельно |
| `WEB_ADMIN_USER` | Логин оператора, по умолчанию `admin`; используйте ASCII |
| `WEB_ADMIN_PASSWORD` | Пароль оператора, минимум 12 символов ASCII |
| `KNOWLEDGE_BACKEND` | `keyword` для редактирования базы знаний через сайт |
| `API_PROXY_TARGET` | Адрес Python-сервера для разработки; по умолчанию `http://127.0.0.1:8000` |
| `WEB_PORT` | Локальный порт контейнера сайта, по умолчанию `8080` |

Нельзя добавлять ключ GigaChat или пароль в переменные с префиксом `VITE_`: такие значения могут попасть в клиентскую сборку.

В первом терминале:

```powershell
.venv\Scripts\python.exe scripts/run_server.py
```

Во втором терминале:

```powershell
npm.cmd run dev
```

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Индикатор сервиса проверяет доступность API, а не успешность авторизации в GigaChat. Проверка реального AI-ответа выполняется отправкой вопроса после настройки ключа.

Если `web/.env` отсутствует, настройки GigaChat могут загружаться из `.env` исходного бэкенда. Для воспроизводимого запуска рекомендуется явно настроить `web/.env`. Сценарий запуска использует рабочий каталог бэкенда, чтобы сохранить корректные пути к базе знаний и SQLite.

На Linux аналогичные команды: `python3.12 -m venv .venv`, `.venv/bin/python -m pip install -r server/requirements.lock`, `.venv/bin/python scripts/run_server.py`, `npm run dev`.

## Развёртывание полного сайта

Загрузите на Linux-сервер обе папки с сохранением структуры:

```text
project/
  1C_Support_Agent/
  web/
```

Требуется Docker Engine с Docker Compose. В `web` создайте `.env` из `.env.example` и задайте настоящие настройки. Не переносите локальные `node_modules`, `.venv`, `.local`, тестовые отчёты, `.git` и секреты в публичные каталоги.

```bash
cd web
cp .env.example .env
```

После заполнения `.env`:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 api web
curl http://127.0.0.1:8080/api/health
```

Compose публикует сайт только на `127.0.0.1:8080`; Python API не публикуется наружу. Для домена и HTTPS поставьте перед ним reverse proxy на сервере. Пример для Caddy находится в [deploy/Caddyfile.example](deploy/Caddyfile.example): замените `support.example.com` своим доменом, направьте DNS на сервер и разрешите необходимые входящие соединения. [Документация Caddy](https://caddyserver.com/docs/quick-starts/reverse-proxy).

Административная авторизация передаёт пароль в HTTP-заголовке, поэтому внешний доступ должен работать через HTTPS. Чат и чтение базы знаний доступны посетителю сайта без личной авторизации. Для корпоративных материалов ограничьте весь сайт VPN, корпоративным SSO или правилами доступа reverse proxy. Реализация индивидуальных учётных записей сотрудников не входит в текущий адаптер.

Nginx ограничивает размер тела запроса и частоту запросов. Настройки находятся в [deploy/nginx.conf](deploy/nginx.conf). При размещении за ещё одним proxy ограничение частоты по IP будет видеть адрес этого proxy, пока вы отдельно не настроите доверенные адреса и передачу реального IP клиента.

Контейнер API запускается одним worker: текущий `SessionManager` хранит активные диалоги в памяти процесса. Увеличивать количество worker или реплик без замены хранилища сессий нельзя. Данные SQLite сохраняются в томе `support_state`, материалы — в томе `knowledge`. Первый запуск создаёт новую БД, а не копирует вашу локальную `support_agent.db`.

База знаний копируется в том при его первом создании. Последующие пересборки образа не заменяют материалы в существующем томе: обновляйте их через сайт или отдельной согласованной миграцией. `docker compose down` сохраняет тома; добавление `-v` удалит их вместе с данными.

Обновление кода:

```bash
docker compose up -d --build
```

Перед обновлением сохраняйте резервную копию БД средствами SQLite и копию тома базы знаний. Не копируйте только основной SQLite-файл во время активной записи, игнорируя WAL.

Контейнерные healthcheck и порядок старта описаны в [документации Compose](https://docs.docker.com/compose/how-tos/startup-order/). Файлы исключений сборки размещены рядом с Dockerfile по [правилам Docker](https://docs.docker.com/build/concepts/context/#dockerignore-files).

## Контракты и адаптация бэкенда

| Маршрут | Реализация |
| --- | --- |
| `POST /api/chat/{id}` | Адаптер к исходному `Session.ask`, сообщение `{ "message": "..." }`; сбои агента возвращаются как HTTP 502 |
| `POST /api/chat/{id}/greeting` | Приветствие исходного агента |
| `POST /api/chat/{id}/feedback` | Исходное сохранение CSAT, оценка 0–10 |
| `POST /api/chat/{id}/file` | Адаптер, multipart `file` + `message`, вызов `Session.analyze_file` |
| `GET /api/health` | Доступность API и возможность редактирования базы знаний |
| `GET /api/knowledge` | Список текущих Markdown/TXT-материалов с содержимым |
| `POST /api/admin/knowledge` | Создание/редактирование; авторизация и контроль версии материала |
| `GET /api/admin/dashboard` | Существующий `AdminPanel.get_dashboard_summary` |
| `GET /api/admin/daily-stats` | Существующий `AdminPanel.get_daily_stats` |
| `GET /api/admin/category-stats` | Существующий `AdminPanel.get_category_stats` |
| `GET /api/admin/escalations` | Существующий `AdminPanel.get_open_escalations` |

Исходный `app/admin/web.py` запускает отдельное FastAPI-приложение. Адаптер размещает методы его `AdminPanel` и API чата в одном приложении, защищая административные маршруты. Старые `/api/dashboard` и `/dashboard` в адаптер не подключаются. Для текстовых сообщений адаптер проверяет `Session.last_request_failed`: обработанный агентом сбой возвращается как HTTP 502, а новый запрос в SQLite получает статус `failed`. Это исправляет исходное поведение, при котором текст ошибки возвращался с кодом 200 и учитывался как успешный ответ.

Для TLS GigaChat приложение использует официальный сертификат из `server/certs` через `GIGACHAT_CA_BUNDLE_FILE`; системное хранилище не меняется. Проверка сертификатов остаётся включённой. Источник и SHA-256: [server/certs/README.md](server/certs/README.md). При необходимости задайте собственный CA bundle этой переменной окружения.

Файловый адаптер сохраняет результат анализа в существующей SQLite-схеме, чтобы работали статистика и оценка. Временный локальный файл удаляется после обработки. Передача изображения в GigaChat выполняется исходным `FileProcessor`; удаление загруженного файла из удалённого хранилища GigaChat исходный бэкенд здесь не реализует.

Маршрут вложений использует блокировку `Session._lock`, потому что исходный класс не предоставляет отдельного публичного метода для атомарного анализа с записью в БД. При изменении внутреннего устройства Session проверьте [server/uploads.py](server/uploads.py) и его интеграционные тесты.

## Соответствие критериям и ограничения

Изучены [Молвест.xlsx](../критерии/Молвест.xlsx), лист `Лист1`, и [Критерии Хакатон 26.pdf](../критерии/Критерии%20Хакатон%2026.pdf), страницы 2–3 с требованиями первого этапа. В интерфейсе не подставлены фиктивные показатели достижения бизнес-целей.

| Требование | Текущее состояние |
| --- | --- |
| Вопросы и ответы по 1С | Интерфейс подключён к исходному API GigaChat-агента |
| Приём скриншотов PNG/JPEG | Реализованы интерфейс и адаптер к существующему анализатору |
| Пополнение и редактирование базы знаний | Реализовано для Markdown/TXT; новые тексты доступны поиску `keyword` без перезапуска |
| Оценка пользователем и аналитика | Подключены существующие методы БД, отсутствие данных отображается явно |
| Эскалации | Просмотр открытых эскалаций; механизм записи эскалаций остаётся в исходном бэкенде |
| Автоматическое подключение оператора | Не реализовано в исходном бэкенде, интерфейс не обещает соединение |
| Bitrix24 / Redmine / почта / чтение существующего чата | Не реализованы; нужны отдельные серверные интеграции |
| Импорт Word/PDF/HTML в базу знаний | Не реализован; доступен текстовый импорт Markdown/TXT |
| Векторная база знаний | Сохраняется возможность использования существующего backend; редактирование через сайт отключено, чтобы не оставлять старый индекс |
| Снижение нагрузки на 30–40%, ответ менее 5 секунд | Цели заказчика, а не измеренные результаты; нагрузочное исследование не проводилось |

История сообщений хранится в `localStorage`. Это не серверный архив и не переносимая между устройствами история. Исходный `SessionManager` может удалить контекст после простоя: обычный TTL — 30 минут, для завершённых сессий — 2 минуты, плюс период фоновой очистки. После перезапуска сервера контекст также теряется. Фронтенд сообщает об этом в истории и справке.

Оценка CSAT привязывается к последнему запросу активной серверной сессии. После её удаления бэкенд вернёт ошибку; интерфейс не подтверждает фиктивное сохранение. Повтор запроса после сетевого сбоя не идемпотентен: исходное API не предоставляет ключей идемпотентности. Сообщение можно вернуть в редактор для осознанной повторной отправки.

Метрика «Успешные ответы» отражает `status='success'` в БД, а не подтверждённое решение проблемы пользователя. Среднее время переводится из миллисекунд в секунды делением на 1000. Динамика показывает последние 14 дат, для которых сервер вернул обращения, без выдуманных значений за отсутствующие дни.

Существующий `Session.ask` записывает текстовые обращения с каналом `cli`, даже если они пришли через HTTP. Фронтенд не показывает эту метку как канал пользователя. Изменение исходного учёта каналов оставлено на стороне бэкенда.

Порог уверенности и правила передачи оператору для текстового чата определяет исходный `Session.ask`. Его файловый путь `Session.analyze_file` не использует тот же механизм эскалации; файловый адаптер не выдумывает уверенность по скриншоту.

Исходники для проверки: [Session](../1C_Support_Agent/app/session/session.py), [SessionManager](../1C_Support_Agent/app/session/session_manager.py), [поиск по материалам](../1C_Support_Agent/app/knowledge/base.py), [AdminPanel](../1C_Support_Agent/app/admin/panel.py), [SQL-представления](../1C_Support_Agent/support_agent_db/schema.sql).

Пользовательская инструкция запрещает комментарии в новом коде. Поэтому архитектура и ограничения описаны здесь, хотя PDF-критерии отдельно упоминают комментарии к сложным участкам.

## Проверки

Результаты выполненных проверок и границы верификации: [VERIFICATION.md](VERIFICATION.md).

```powershell
npm.cmd run build
npm.cmd test
npm.cmd run test:e2e
.venv\Scripts\python.exe -m pytest tests/test_gateway.py tests/test_timeout.py -q
```

Браузерные тесты используют установленный Google Chrome. Если его нет, установите Chromium через `npx playwright install chromium` и уберите `channel: 'chrome'` из `playwright.config.ts`.

Тесты адаптера используют настоящие Session, FastAPI и временную SQLite-базу с тестовой заменой AI-агента. Браузерные тесты используют контролируемые ответы API. Секреты, внешние запросы к GigaChat и рабочая БД для этих тестов не нужны.

Реальный ответ GigaChat проверен локально после настройки сертификата приложения. Запуск Docker-образов и публикация на домене требуют отдельной проверки в целевом окружении и здесь не заявляются как выполненные.
